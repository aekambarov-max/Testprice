# Price — подмодуль «Маркетинговый анализ с маршрутом согласования» (MVP)

ИС «Маркетинг цен, учёт закупа и складского запаса», модуль **Price**. Подмодуль, в котором маркетинговый анализ
инициирует сам Маркетолог ДЗО. После анализа документ проходит маршрут согласования с участием Департамента
бюджетирования КМГ и утверждается директором ДБ. Итог работы — PDF «Маркетинговое заключение».

> **Важно: это MVP, собранный с нуля.** Кода действующего модуля Price (price.kmg.kz) в репозитории нет. Поэтому
> справочники и сервисы, которые по ТЗ нужно переиспользовать (АСУ НСИ, ДЗО, пользователи и роли, пул поставщиков
> и рассылка запросов КП, расчёт маркетинговой цены, каталог цен, аудит, уведомления), реализованы здесь в
> минимальном виде как отдельные приложения `apps/*` с теми же границами. При переносе в настоящий репозиторий
> их нужно заменить вызовами существующих сервисов. Подмодуль (`apps/marketing_analysis`) обращается к ним
> только через их сервисные функции.

Стек: Python 3.11+, Django 5.2 + DRF, Celery + Redis, PostgreSQL 17, WeasyPrint (PDF без внешних сервисов),
Vue 3 + Vite, nginx, Docker. Интерфейс на русском и казахском языках.

## Быстрый старт

### Локально (без Docker)

```bash
# backend
python3 -m venv .venv && . .venv/bin/activate
pip install -r backend/requirements-dev.txt
cd backend
python manage.py migrate
python manage.py seed_demo          # ДЗО, пользователи 5 ролей, товары НСИ, поставщики, курсы, история каталога
python manage.py runserver 8000     # без DATABASE_URL — SQLite, Celery-задачи выполняются синхронно

# frontend (в другом терминале)
cd frontend && npm install && npm run dev   # http://localhost:5173, /api проксируется на :8000
```

Для WeasyPrint нужны системные библиотеки Pango (`libpango-1.0-0`, `libpangoft2-1.0-0`).

### Docker (тестовый стенд / on-premise)

```bash
cp .env.example .env   # задать пароли, хосты и SMTP
docker compose up -d --build
docker compose exec backend python manage.py seed_demo   # только для тестового стенда
# http://localhost:8080
```

Состав: `db` (PostgreSQL 17.2), `redis`, `backend` (gunicorn, миграции при старте), `worker` (Celery: PDF,
уведомления, рассылка КП), `frontend` (nginx: SPA и прокси `/api`). Каталог `/media` наружу не публикуется:
файлы КП и заключения отдаются только через API с проверкой прав.

## Процесс

1. **Маркетолог** создаёт анализ. Указывает инициатора: сотрудника из справочника или вручную (ФИО обязательно,
   должность и подразделение по желанию). ДЗО по умолчанию берётся из профиля пользователя; выбрать можно только
   ДЗО, к которым у маркетолога есть доступ. Номер присваивается сразу, поэтому ДЗО после создания не меняется.
2. Добавляет позиции: товар ищется по коду АСУ НСИ или наименованию. Код НСИ, код ЕНС ТРУ, наименование,
   характеристика и единица измерения сохраняются **снимком** в позиции. Вручную вводятся количество, место и
   срок поставки, к позиции можно приложить файлы.
3. Направляет поставщикам из пула **запросы КП**. Поставщик получает письмо со ссылкой `/kp/{token}` и может
   подать КП онлайн; такое КП само попадает в анализ.
4. Загружает КП: файл, БИН с проверкой контрольного разряда, дата, валюта, цены с НДС или без. Цены
   пересчитываются в тенге без НДС по курсу НБ РК на дату КП. Кнопка «Рассчитать» вызывает сервис расчёта
   (`apps/pricing`) и строит аналитику: диаграмму цен участников, историю каталога цен, среднюю по группе КМГ,
   отклонение от неё. Любое изменение КП сбрасывает рассчитанную цену позиции.
5. Выбирает согласующих этапа 1 и задаёт их порядок перетаскиванием, затем нажимает «Отправить на согласование».
6. Маршрут проходит **последовательно**: этап 1 (согласующие ДЗО) → этап 2 (Специалист ДБ КМГ) → этап 3
   (Директор ДБ КМГ, утверждение). На каждом шаге можно согласовать (комментарий не обязателен) или вернуть на
   доработку (комментарий обязателен).
7. После утверждения позиции попадают в **Каталог цен** как действующее исследование, а Celery-задача формирует
   PDF-заключение. Файл неизменяемый, для него сохраняется SHA-256; повторное скачивание отдаёт тот же файл.

## Статусы

| Код | Статус | Кто действует | Переходы |
|---|---|---|---|
| `draft` | Черновик | Маркетолог | → `collecting_kp` (явно, при первом КП или запросе КП), → `cancelled` |
| `collecting_kp` | Сбор КП | Маркетолог | → `on_approval_dzo`, → `on_approval_db` (если разрешено без этапа 1), → `cancelled` |
| `on_approval_dzo` | На согласовании (ДЗО) | Согласующие этапа 1 по очереди | → `on_approval_db`, → `rework` |
| `on_approval_db` | На согласовании ДБ КМГ | Специалист ДБ КМГ | → `on_final_approval`, → `rework` |
| `on_final_approval` | На утверждении директора ДБ КМГ | Директор ДБ КМГ | → `approved`, → `rework` |
| `rework` | На доработке | Маркетолог | повторная отправка (маршрут заново или с вернувшего этапа), → `cancelled` |
| `approved` | Утверждено | — | конечный, формируется PDF |
| `cancelled` | Аннулировано | — | конечный |

Все переходы выполняются только в `apps/marketing_analysis/workflow.py`. Каждый переход идёт в транзакции:
строка блокируется через `select_for_update`, проверяются ожидаемый статус и текущий исполнитель шага, а сам
переход пишется в журнал аудита (кто, когда, откуда, куда, комментарий, IP). Двойное нажатие или устаревшая
страница дают `409` (`status_changed` / `step_already_processed`). Данные анализа можно менять только в статусах
`draft`, `collecting_kp` и `rework`.

## Роли и права

Роли — группы Django, они создаются миграцией `core.0002_roles`: `marketer`, `db_specialist`, `db_director`,
`ma_admin`. «Согласующий ДЗО» — не роль, а участие в маршруте конкретного анализа.

| Действие | Маркетолог | Согласующий ДЗО | Специалист ДБ | Директор ДБ | Администратор |
|---|---|---|---|---|---|
| Создание и редактирование, КП, расчёт, согласующие, отправка | ✔ (свои ДЗО) | | | | |
| Просмотр карточки | ✔ (свои ДЗО) | ✔ (где участник) | ✔ (все) | ✔ (все) | ✔ |
| Решение, этап 1 | | ✔ (свой шаг) | | | |
| Решение, этап 2 | | | ✔ | | |
| Решение, этап 3 | | | | ✔ | |
| Скачать PDF | ✔ | ✔ | ✔ | ✔ | ✔ |
| Повторно сформировать PDF после ошибки, справочники (Django admin) | | | | | ✔ |

Права проверяются на backend дважды: на уровне queryset (`access.visible_analyses`, чужой анализ по ID → `404`)
и на уровне действия. В ответе карточки есть поле `available_actions`, и интерфейс показывает только эти кнопки.
Пункт меню «Маркетинговый анализ» видят роли из таблицы, а согласующие ДЗО — если участвуют хотя бы в одном
маршруте.

## API

Все эндпоинты лежат под `/api/marketing-analyses/`: реестр с фильтрами `tab`, `status`, `dzo`, `date_from`,
`date_to`, `nsi_code`, `author`, `q` и счётчиками `counts` для табов; карточка (`GET`/`PATCH`/`DELETE`);
`items/`, `items/{id}/`, `items/{id}/attachments/`; `offers/` (multipart), `offers/{id}/`; `request-kp/`,
`start-collecting/`, `calculate/`, `analytics/`, `approvers/` (`PUT`), `submit-check/`, `submit/`, `decision/`
(`{"decision": "approve"|"rework", "comment", "step_id"}`), `cancel/`, `history/`, `conclusion.pdf`,
`regenerate-pdf/`.

Справочники: `/api/nsi/products/?q=`, `/api/users/search/?q=&dzo=`, `/api/dzos/`, `/api/suppliers/?q=`,
`/api/price-catalog/?q=`. Сессия: `/api/auth/me|login|logout/`. Уведомления: `/api/notifications/`.
Ответ поставщика на запрос КП (публичная ссылка): `/api/kp-responses/{token}/`.

## Тесты

```bash
cd backend && pytest                                      # SQLite
DATABASE_URL=postgres://... pytest                        # + тест одновременных решений (select_for_update)
cd frontend && npm test                                   # vitest: степпер, экран решения, табы
```

Покрыто тестами:
- **state machine** — все переходы, повторная отправка с этапа 1 и с вернувшего этапа, отправка без этапа 1;
- **матрица прав** по ролям, 404 на чужие анализы;
- **валидации** перед отправкой и запрет редактирования после неё;
- **конкурентность** — двойное нажатие, одновременные решения двух специалистов ДБ (на PostgreSQL);
- **PDF** — номер, позиции, лист согласования, казахские буквы, хэш при повторном скачивании; сбой генерации
  не откатывает утверждение;
- **устойчивость уведомлений** — ошибка брокера не откатывает смену статуса;
- **КП и расчёт** — расчёт цены, НДС и курсы, БИН, приём КП от поставщика по ссылке.

## Что в MVP заглушено (нужно подключить к действующему Price)

- **Справочники и интеграции.** АСУ НСИ / ЕНС ТРУ, ДЗО и пользователи — локальные таблицы, в проде их наполняет
  интеграция через SAP PI/PO и LDAP. ГБД ЮЛ: проверяется только контрольный разряд БИН и ищется совпадение в пуле
  поставщиков.
- **Вход.** Только локальные учётные записи; LDAP/AD подключается через `django-auth-ldap`.
- **Остальные разделы портала.** «Заявки», «Пул поставщиков», «Каталог цен», «Аналитика» в меню — заглушки для
  навигации.
- **Цвета и логотип.** Фирменный синий и логотип КМГ в PDF подобраны приблизительно, их нужно сверить с брендбуком.
